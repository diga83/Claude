1. Computational Thinking — The Big Picture

Computational thinking means approaching a problem the way a computer scientist does — analysing it logically so that a computer (or a person following precise steps) could solve it. It is NOT "thinking like a computer"; it is thinking about problems in a way that makes them solvable by computers. Topic 1 of the 4CP0 specification is built on three connected ideas:

TechniqueOne-line definitionQuestion it answers
DecompositionBreaking a large problem into smaller, more manageable sub-problems"What separate parts make up this problem?"
AbstractionRemoving or hiding unnecessary detail so only the essential features remain"What actually matters here, and what can I ignore?"
Algorithm designWriting a precise sequence of steps that solves each sub-problem (Chapter 2)"What exact steps solve it?"
📋 SPEC 1.2.1

Understand the benefit of using decomposition and abstraction to model aspects of the real world and analyse problems and systems.

💡 Why This Topic Opens the Course

Every other topic depends on these two ideas. Algorithms (Topic 1.2) are designed for the sub-problems decomposition produces. Subprograms in Python (Topic 6) are decomposition written as code. Even binary itself is an abstraction — a voltage in a wire is "abstracted" to the symbol 1 or 0.

2. Decomposition — Breaking Problems Down

Decomposition is breaking a large, complex problem down into smaller, more manageable sub-problems. Each sub-problem can then be understood, solved and tested separately — and, if it is still too big, decomposed again. When the solution is eventually programmed, each sub-problem typically becomes a subprogram (a function or procedure).

2.1 Worked Example — Decomposing a Computer Game

Suppose you are asked to write a simple arcade game. "Write a game" is far too big to tackle in one go. Decomposed, it becomes a set of clear, separate jobs:

PROBLEM: Build an arcade game
├── 1. Display the game world (draw background, sprites, score)
├── 2. Handle player input (keyboard / controller presses)
├── 3. Move the player's character
├── 4. Move the enemies
│     ├── 4a. Decide each enemy's direction
│     └── 4b. Detect collisions with walls
├── 5. Detect collisions between player and enemies
├── 6. Update and display the score
└── 7. Check for game over and show the final screen

Notice that sub-problem 4 was still too large, so it was decomposed again. You stop decomposing when each sub-problem is small enough to design an algorithm for directly.

2.2 The Four Benefits of Decomposition

BenefitWhy it helpsExam-ready phrasing
Simpler problemsSmall sub-problems are easier to understand and solve than one huge problem"Each sub-problem is smaller and easier to solve than the whole problem"
TeamworkDifferent people (or teams) can work on different sub-problems at the same time"Sub-problems can be developed in parallel by different programmers, so the solution is finished sooner"
ReuseA solved sub-problem (e.g. "validate a date") may already exist or can be reused in other projects"Existing/library solutions to sub-problems can be reused, saving development time"
Easier testing & debuggingEach part can be tested on its own, so errors are found and isolated quickly"Each sub-problem can be tested separately, making errors easier to locate and fix"
⚡ EXAM TIP

When a question asks for benefits of decomposition, never just write "it makes the problem easier". Develop the point: easier because each sub-problem is smaller, can be solved/tested independently, and can be shared across a team. The development is what earns the second mark.

2.3 Decomposition → Subprograms

Decomposition is not just a paper exercise — it maps directly onto code. Each sub-problem becomes a named subprogram, and a short main program calls them in order:

# Each sub-problem from the game becomes a subprogram
def draw_world():
    ...            # sub-problem 1

def handle_input():
    ...            # sub-problem 2

def move_enemies():
    ...            # sub-problem 4

def check_collisions():
    ...            # sub-problem 5

# Main game loop — reads like the decomposition itself
while not game_over:
    handle_input()
    move_enemies()
    check_collisions()
    draw_world()
📌 Link to Spec 1.2.2

The benefits of subprograms mirror the benefits of decomposition: code is easier to read, write, test and debug; subprograms can be reused; and teams can write different subprograms simultaneously. You will meet subprograms properly in the Python chapters — for now, remember that decomposition is the planning step and subprograms are the coding step.

3. Abstraction — Removing Unnecessary Detail

Abstraction is removing or hiding unnecessary detail so that you can concentrate on the essential features of a problem. The result is a simplified model of the real world that contains only what is needed for the task. What counts as "unnecessary" depends entirely on the purpose of the model.

3.1 The Classic Example — The London Underground Map

The London Underground map (designed by Harry Beck in 1931) is the example almost every examiner expects. A passenger planning a journey needs to know which line to take, where to change, and how many stops remain. They do NOT need real distances, street layouts or the depth of tunnels — so the map removes all of that:

KEPT (essential detail)REMOVED (unnecessary detail)
Station names and their order along each lineReal geographical distances between stations
Which line each station is on (colour-coded)The actual curved routes the tunnels take
Interchange stations where passengers can change linesStreets, buildings and surface geography
The River Thames (a rough position guide)Depth of tunnels, engineering details, timetables

The abstracted map is less accurate but more useful — because it matches the passenger's purpose. That trade-off is the heart of abstraction.

3.2 Abstraction in Games and Models

A computer game is an abstraction of the real world. A football game models the pitch, the ball, player positions and the score — the essentials of football. It does not model the grass growing, the weather in neighbouring towns, or each spectator's thoughts, because none of that affects gameplay. Similarly:

ModelPurposeDetail keptDetail removed
Driving gameFun, believable drivingSpeed, steering, track layout, collisionsEngine chemistry, tyre temperature physics, fuel economy
Weather forecast modelPredict tomorrow's weatherAir pressure, temperature, wind, humidity readingsIndividual clouds, leaves blowing, exact raindrop positions
School timetable systemSchedule lessons without clashesTeachers, classes, rooms, periods, subjectsRoom colour, what teachers wear, the content of each lesson
Flight simulatorTrain pilots safelyCockpit controls, physics of lift/drag, instrument readingsPassengers' conversations, in-flight meals, cabin decor

3.3 Variables Are Abstractions Too

When you write a program, every variable is an abstraction. A real player in a quiz has a face, a voice and a history — but if the program only needs to track their progress, all of that is abstracted away to a few values:

# A real-world player abstracted to just the data the program needs
player_name  = "Asha"     # string — identifies the player
score        = 0          # integer — tracks progress
lives        = 3          # integer — remaining attempts
is_playing   = True       # Boolean — current state

# A whole class of 30 real students abstracted to a list of marks
marks = [56, 72, 38, 91, 64]
⚡ EXAM TIP

"State what is meant by abstraction" is a bankable 1-mark question. Learn the exact wording: "removing or hiding unnecessary detail so that the essential features of a problem can be focused on". For a second mark, apply it: say WHICH detail is removed in the given scenario and WHY it is not needed for the purpose.

4. Pattern Recognition — The Supporting Idea

Pattern recognition means spotting similarities — between sub-problems within one project, or between a new problem and ones already solved. It is not a separately named bullet in the 4CP0 specification, but it underpins the "reuse" benefit of decomposition and appears naturally in good exam answers.

Where the pattern appearsExamplePay-off
Within one programValidating a username and validating a password are both "check input against rules"Write ONE validation subprogram, call it twice with different rules
Across problemsFinding the highest test mark and finding the most expensive product are both "find the maximum in a list"Reuse the same maximum-finding algorithm (see Chapter 2)
Across projectsEvery game needs a main loop: input → update → drawReuse the structure of a previous game as a starting template
💡 How the Three Ideas Work Together

Decompose the problem into sub-problems → recognise patterns so similar sub-problems share one solution → abstract each sub-problem to its essential data and rules → design an algorithm for each. This pipeline is exactly what examiners want to see in 6-mark "analyse this problem computationally" answers.

5. Worked Scenario — Analysing a Problem Computationally

Exam questions give you an unfamiliar scenario and ask you to apply decomposition and/or abstraction to it. Work through this one carefully — the method matters more than the scenario.

🎯 Scenario: A Car-Park Ticket Machine

A company wants software for a car-park ticket machine. Drivers enter their registration number and the number of hours they want to park, pay, and receive a printed ticket. The machine must also report daily takings to the office.

5.1 Step 1 — Decompose

PROBLEM: Car-park ticket machine software
├── 1. Read and validate the registration number entered
├── 2. Read and validate the number of hours (e.g. 1–24)
├── 3. Calculate the price (hours × hourly rate)
├── 4. Take payment
│     ├── 4a. Accept coins / card
│     └── 4b. Calculate and give change (coins only)
├── 5. Print the ticket (registration, expiry time, price)
└── 6. Record the transaction and send daily totals to the office

5.2 Step 2 — Abstract

Essential — keepUnnecessary — remove
Registration number (string)The make, colour and size of the car
Hours requested and expiry timeWhy the driver is parking; where they are going
Hourly rate and price (number)The driver's name and appearance
Amount paid and change dueWhich pocket the coins came from
Running total of takingsThe weather, the time it takes to type, queue length

The whole car-park problem has been reduced to a handful of variables (reg, hours, rate, price, paid, takings) and six sub-problems, each small enough to design an algorithm for. That is computational analysis — and it is exactly the skill Chapter 2 builds on.

⚠️ Decomposition or Abstraction? Don't Mix Them Up

Decomposition splits a problem into PARTS. Abstraction strips a problem of DETAIL. Splitting the ticket machine into "validate input / calculate price / print ticket" is decomposition. Deciding to ignore the car's colour is abstraction. Many candidates lose easy marks by defining one when asked about the other — check which word is in the question before writing.

6. Decomposition vs Abstraction — Side by Side

DecompositionAbstraction
DefinitionBreaking a problem into smaller, more manageable sub-problemsRemoving or hiding unnecessary detail to focus on essential features
Acts onThe STRUCTURE of the problem (its parts)The DETAIL of the problem (what to include in the model)
ResultA set of smaller sub-problems / subprogramsA simplified model containing only what matters
Classic exampleSplitting a game into draw / input / update / scoreThe London Underground map
In codeFunctions and procedures (subprograms)Variables, lists and data structures representing real things
Key exam verb"Break down", "split", "sub-problem""Remove", "ignore", "hide", "essential detail"
⚡ EXAM TIP — They Are Used TOGETHER

Higher-mark questions often ask how BOTH techniques help analyse one scenario. Structure your answer: (1) decompose — name two or three sensible sub-problems from the scenario; (2) abstract — name one detail to keep and one to discard, with a reason tied to the purpose; (3) state the benefit — the problem becomes simple enough to design algorithms for each part.

7. Model Answers

Study the structure of each answer. Marks are shown with (1) — notice how every mark point is a distinct, developed idea, not a repeat of the question.

✎ MODEL ANSWER

[2 marks]

Question: Describe what is meant by decomposition. [2 marks]

Decomposition is breaking a large or complex problem down into smaller sub-problems (1). Each sub-problem is more manageable and can be solved, tested or programmed separately (1).

Why this scores full marks: ✓ First mark — the core definition: breaking a problem into smaller sub-problems ✓ Second mark — a development: the sub-problems can be handled separately. "Describe" needs more than a bare definition; the second sentence supplies the extra substance without padding.

✎ MODEL ANSWER

[3 marks]

Question: The London Underground map is often described as an abstraction. Explain why. [3 marks]

Abstraction means removing unnecessary detail so that only the essential features remain (1). The Underground map removes detail a passenger does not need, such as real distances between stations, the actual routes of the tunnels and the street layout above ground (1). It keeps only the essential information for planning a journey — the order of stations on each line and the interchange stations where passengers can change lines — which makes the map easier to use for its purpose (1).

Why this scores full marks: ✓ Defines abstraction first, anchoring the answer ✓ Names SPECIFIC removed details (distances, routes, streets) — vague "it leaves stuff out" would not score ✓ Names the KEPT essentials and links them to the purpose (journey planning) — purpose is what justifies the abstraction and earns the third mark.

✎ MODEL ANSWER

[4 marks]

Question: A team of programmers is building software for a vending machine. Explain two benefits of using decomposition when developing this software. [4 marks]

One benefit is that the team can work on different sub-problems at the same time (1) — for example, one programmer writes the code that takes payment while another writes the code that releases the chosen item, so the software is completed more quickly (1). A second benefit is that each sub-problem can be tested separately (1) — if the change-giving code returns the wrong coins, the error must be inside that sub-problem, so it is much faster to locate and fix than searching the whole program (1).

Why this scores full marks: ✓ Two DIFFERENT benefits, each one named clearly (parallel working; separate testing) ✓ Each benefit developed with a consequence ("completed more quickly", "faster to locate and fix") ✓ Both points are tied to the vending machine scenario, not left generic — scenario-specific development is what converts 2 marks into 4.

8. Common Mistakes

✗ COMMON MISTAKES — DON'T DO THESE!

✗ Swapping the definitions — decomposition splits a problem into PARTS; abstraction removes DETAIL. Read the question word carefully; defining the wrong one scores zero.

✗ Defining abstraction as "making the problem simpler" with no mention of removing/hiding unnecessary detail — "simpler" alone is too vague to earn the mark.

✗ Giving decomposition benefits without development — "it makes it easier" scores nothing. Say WHY: sub-problems are smaller, can be tested separately, can be shared across a team.

✗ Decomposing into steps that are really just one step reworded — "make the game", "build the game", "create the game" is not decomposition. Sub-problems must be genuinely different tasks.

✗ When asked to abstract a scenario, listing detail to REMOVE but never saying what to KEEP — examiners want both sides, each justified by the purpose of the model.

✗ Claiming abstraction means the model is "wrong" or "inaccurate" — an abstraction is deliberately simplified FOR A PURPOSE; it keeps everything the purpose requires.

✗ Forgetting the code connection — when a question mentions programming, link decomposition to subprograms (each sub-problem becomes a function/procedure that can be written and tested separately).

✗ Writing about hardware, binary or networks in a Spec 1.2 answer — this topic is about ANALYSING problems. Keep answers focused on sub-problems, detail and models.

10. Quick Reference — Key Terms & Revision

★ QUICK REFERENCE — KEY TERMS

Computational thinking: Analysing problems logically — using decomposition, abstraction, pattern recognition and algorithm design — so that a computer could solve them

Decomposition: Breaking a large problem down into smaller, more manageable sub-problems that can be solved independently

Sub-problem: One of the smaller parts produced by decomposition; small enough to design an algorithm for, and typically programmed as a subprogram

Abstraction: Removing or hiding unnecessary detail so the essential features of a problem can be focused on

Model: A simplified (abstracted) representation of part of the real world, built for a specific purpose — e.g. a game world, a weather model, the Tube map

Pattern recognition: Spotting similarities between problems or sub-problems so an existing solution can be reused

Subprogram: A named block of code (function or procedure) that solves one sub-problem and can be called whenever needed

Variable: A named memory location storing one value — itself an abstraction of a real-world quantity (e.g. score, lives)

Benefits of decomposition (learn all four): ① smaller/simpler sub-problems ② different people can work in parallel ③ solutions can be reused ④ parts can be tested and debugged separately

Abstraction method (apply in scenarios): state the PURPOSE of the model → KEEP detail the purpose needs → REMOVE detail it does not → justify both
